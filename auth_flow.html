Nomor 8: Alur Autentikasi dan Perbandingan Session vs JWT

1. Alur Login Berbasis Session (Implementasi Proyek)

Alur autentikasi berbasis sesi pada sistem ini bekerja secara stateful. Proses diawali saat pengguna mengirimkan kredensial (alamat email dan kata sandi) melalui form login ke endpoint /api/login.php. Server kemudian mencari data pengguna di database MySQL berdasarkan email dan memverifikasi kecocokan hash kata sandi menggunakan fungsi password_verify(). Jika kredensial salah, server menolak akses dengan respons 401 Unauthorized dan pengguna tetap berada pada halaman login. Apabila kredensial valid, server segera memanggil session_regenerate_id(true) untuk mengacak ulang ID sesi demi mencegah serangan Session Fixation, menyimpan data identitas penting (user_id dan role) di dalam variabel global $_SESSION di memori server, serta mengirimkan cookie PHPSESSID yang telah diamankan dengan atribut HttpOnly, SameSite=Lax, dan Secure (pada HTTPS) ke peramban pengguna untuk digunakan pada request-request berikutnya.

2. Alur Hipotetis Login Berbasis JSON Web Token (JWT)

Pada arsitektur alternatif berbasis JWT (JSON Web Token), proses autentikasi berlangsung secara stateless. Klien mengirimkan kredensial dalam payload JSON ke endpoint login. Server melakukan verifikasi email dan kata sandi terhadap database. Apabila validasi berhasil, server tidak membuat berkas sesi pada memorinya, melainkan mengenerate string token JWT yang terdiri dari tiga bagian: Header (algoritma enkripsi), Payload (data identitas pengguna seperti user_id dan role serta masa kedaluwarsa exp), dan Signature (tanda tangan digital yang dibentuk menggunakan kunci rahasia server/secret key). Token ini kemudian dikembalikan kepada klien dalam respons JSON. Klien bertugas menyimpan token tersebut secara mandiri dan wajib menyematkannya di dalam header HTTP Authorization: Bearer <token> pada setiap request berikutnya, di mana server hanya perlu memverifikasi tanda tangan kriptografis token tanpa perlu mencocokkannya ke database maupun session store.

3. Penjelasan Perbedaan Arsitektur: State, Penyimpanan Token, dan Logout/Revocation

A. Perbedaan State (Stateful vs Stateless):
Sistem autentikasi berbasis Session bersifat stateful. Artinya, server bertanggung jawab penuh untuk menyimpan status dan konteks pengguna di memorinya (baik dalam bentuk berkas sesi di server maupun cache terdistribusi seperti Redis). Klien hanya memegang identitas referensi berupa Session ID. Konsekuensinya, jika server mengalami restart atau dilakukan horizontal scaling ke beberapa server, seluruh node server harus saling tersinkronisasi atau menggunakan penyimpanan sesi terpusat. Sebaliknya, autentikasi berbasis JWT bersifat stateless. Server tidak menyimpan rekaman sesi apa pun setelah token dibuat. Semua klaim pengguna (identitas, peran, masa berlaku) termaktub di dalam payload token itu sendiri dan diverifikasi menggunakan kunci kriptografi. Hal ini memungkinkan skalabilitas horizontal yang sangat cepat karena server mana pun yang memegang secret key dapat memverifikasi token tanpa perlu membaca basis data.

B. Perbedaan Penyimpanan Token (Token Storage):
Pada arsitektur sesi, Session ID disimpan di dalam Cookie peramban. Tingkat keamanannya sangat tinggi karena dapat dikonfigurasi dengan flag HttpOnly (mencegah script JavaScript pihak ketiga membaca isi cookie sehingga kebal dari serangan pencurian XSS), SameSite=Lax atau Strict (memitigasi pengiriman cookie lintas domain yang menjadi celah serangan CSRF), serta Secure (memastikan cookie hanya ditransmisikan melalui kanal HTTPS terenkripsi). Sedangkan pada arsitektur JWT, token biasanya dikembalikan dalam body JSON dan disimpan oleh klien pada localStorage atau sessionStorage. Penyimpanan di Web Storage ini rentan terhadap eksfiltrasi data apabila website memiliki kerentanan Cross-Site Scripting (XSS). Opsi penyimpanan JWT yang lebih aman adalah menyimpannya di dalam Cookie HttpOnly, namun hal ini meniadakan keunggulan stateless murni karena membutuhkan mekanisme proteksi CSRF token tambahan.

C. Perbedaan Mekanisme Logout dan Revocation:
Mekanisme logout pada session bersifat instan dan deterministik. Ketika pengguna melakukan logout, server cukup mengeksekusi session_destroy() dan mengosongkan berkas sesi di server. Seketika itu juga, Session ID yang tersisa di peramban klien menjadi tidak valid lagi secara absolut, sehingga tidak ada request baru yang dapat dilakukan menggunakan sesi tersebut. Berbeda halnya dengan JWT, di mana proses pembatalan token (token revocation) merupakan tantangan terbesar arsitektur stateless. Sekali sebuah token JWT ditandatangani dan diterbitkan, token tersebut akan tetap sah digunakan oleh siapa pun yang memegangnya hingga waktu kedaluwarsanya (exp) habis, meskipun pengguna sudah menekan tombol logout di antarmuka web. Untuk mengatasi kelemahan ini dalam lingkungan produksi, arsitektur JWT terpaksa kembali menerapkan komponen stateful tambahan, seperti membuat daftar blokir (Token Blacklist / Denylist) di Redis atau menerapkan masa aktif token yang sangat pendek (misal 5-15 menit) yang dipadukan dengan Refresh Token Rotation.

Dimensi Perbandingan Autentikasi Session (Proyek Kita) Autentikasi JWT (Hipotetis)
Karakteristik State Stateful: Server menyimpan sesi pengguna (di disk/memori). Server memegang kendali penuh atas identitas pengguna aktif. Stateless: Server tidak menyimpan sesi. Token mandiri (self-contained) membawa data pengguna dan divalidasi via signature.
Penyimpanan di Klien Cookie HTTP dengan flag HttpOnly, SameSite=Lax, dan Secure. Kebal terhadap serangan pencurian via JavaScript (XSS). Umumnya disimpan di localStorage atau sessionStorage (rentan XSS) atau di cookie HttpOnly.
Proses Logout & Revocation Instan: Server menghancurkan sesi via session_destroy(). Sesi seketika mati dan tidak bisa dipakai lagi. Tantangan Besar: Token tetap valid sampai waktu kedaluwarsa (exp) habis kecuali ditambahkan stateful Blacklist/Redis.
Beban Server Membutuhkan memori/storage untuk menyimpan sesi aktif berbanding lurus dengan jumlah pengguna yang login. Beban penyimpanan di server nihil, namun memerlukan pemrosesan CPU untuk verifikasi signature kriptografis setiap request.
